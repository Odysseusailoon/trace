Forkscope: Measuring Where Agent Trajectories Fork

YUXI ZHENG · SEP 2026 · WORKING NOTES · QWEN3-8B + SGLANG, DETERMINISTIC INFERENCE

An LLM agent's behavior is a distribution over trajectories. Any single run is one draw from it. We built a replay instrument that measures, for any decision step, the counterfactual outcome distribution od: what would have happened had the dice landed differently. With it we find single tokens that lock an episode's fate, benchmark questions where the model's majority answer is wrong, forks the model walks into confidently (invisible to entropy monitoring), and a thinking budget that multiplies success 50×. Every number below is measured, and the preregistered parts are marked. The whole study cost about $60 of GPU time.

1 · How we sample: replay at decision boundaries

Record one episode (T=1.0, tools really execute). At each decision boundary d, rewind to that exact state and sample K=50 full counterfactual continuations — tools re-execute, outcomes are checked against executable gold. The outcome histogram is od; where it collapses is where fate locks.

continuation → correct continuation → trap other / no answer

Replay looks quadratic (K × D full re-prefills). With RadixAttention prefix sharing, the trunk is prefilled once: we measured a 99.2% cache hit over a 6.5M-token replay workload, which makes replay 67–206× cheaper than naive re-prefill. Reruns are bit-identical from derived seeds, so every number on this page can be regenerated.

2 · Token level: wavering is not forking

Chain-of-thought MCQ, outcome distribution over answer options as generation proceeds. This case (virology, 8B) swings between options B and C at 11 measured positions across 600 tokens and never locks. A method that calls every wobble a fork would be wrong here, and the changepoint smoother correctly refuses to. Decision-type forks turned up in about 1% of our 201 MCQ probes. The fork structure worth studying lives in the agent domain.

3 · Agent level: fate is sealed in four tokens

Task: "average albums per artist" over a real SQLite DB. The tool schema primes an integer-division trap (returns 1.000, raises no error, 0% self-repair). Inside the first SQL-writing turn we truncate the prefix at every token, resample 20 continuations each, and classify the emitted SQL. Amber = trap cluster, green = correct cluster. Dashed line = token entropy of the base path.

intdiv (trap → 0% accuracy) AVG+GROUP BY (→ 100%) other entropy (bits)

The turn has two entropy peaks and only one is a fork. At t=17, writing  COUNT (H=1.31, the turn's maximum), the outcome distribution starts collapsing, and four tokens later it is welded shut. At t=28, naming an alias  Average… (H=1.02), the distribution does not move at all. Hesitation and fate are different things, and only measurement tells them apart.

4 · In the wild: BIRD, where the model’s majority is wrong

Same instrument, external benchmark (BIRD mini-dev, 10 questions selected by a frozen two-stage rule: text criteria, then an uncertainty screen keeping questions whose 10-episode answer mode is 4–6 — dispersion, not correctness). 200 episodes per question. Non-thinking Qwen3-8B sits near the floor, and the floor has structure.

correct wrong no answer (mostly intent-stall)

Three findings hide in the floor. First, intent-stall: in the schema-heavy financial DB, up to 56% of episodes hit a column error, write "Let's check the available tables…", then voluntarily stop with budget and turns to spare. Announcing an action and executing it are separable events. Second, same opening, different fates: on b218 the most common correct first SQL is byte-identical to the most common wrong one. The fork sits mid-game, in how results get read, and where a task forks is a property of that task. Third, thinking: with the same weights and seeds, enabling the thinking budget takes b39 from 1/200 correct to 51/200.

5 · Can entropy find the forks? Mostly — and the misses are the story

Cheap idea: only measure where the model hesitates. We tested it on the Forking Fast public release (Llama-3-8B, 100 questions, S=200 ground-truth ot grids): gate positions by 1−pbase, check recall of PELT-detected forks. Amber = entropy-gated recall, olive = random-gate null.

Gating works: about 2× enrichment over random, and recall rises with fork size (0.87 at top-20% for large forks, 0.95 at top-30%). A two-stage instrument, entropy screen first and replay only at gated positions, cuts measurement cost 3–5×. But 13–29% of forks happen where the model is confident. No entropy-based monitor can see them, and the agent data shows why that matters: after the die lands, the trap path in §3 runs at near-zero entropy, confidently doomed.

6 · Fork distributions as a fairer eval

Single-sample evals score one draw from a random variable. Two measured cases show how that lies. On the schema-trap task the modal answer cluster is wrong (46% trap, 18% correct), so greedy and majority-vote evals reward the error. On BIRD b226 the model is a genuine coin flip (o₀ = 0.45).

correct mass modal wrong cluster other outcomes

The distributional alternative is a brittleness profile: success probability o₀ with a confidence interval, the step where fate locks, the self-repair rate, and the coverage of correct strategies. It costs more samples than pass@1, but the same rollouts also provide the attribution in sections 1–4, and prefix caching pays most of the bill. On tasks where the mode is wrong, any eval that trusts the mode rewards the trap. Self-consistency included.
